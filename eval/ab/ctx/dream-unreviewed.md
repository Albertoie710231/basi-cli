# Lessons

## Code map
- Slash commands are dispatched inside main() in src/main.c as a chain of strcmp(user_input, "/<cmd>") branches inside the REPL loop; the /cost branch is the template for a new command — it prints dim grey via printf("\033[90m") and its body currently emits the literal string "BASI-CLI v0.1", then resets with printf("\033[0m\n").  <!-- 20260501-142925.jsonl#0 -->
- /cost prints dim grey output by emitting the ANSI code \033[90m before its text; /version should use the same prefix for matching colour. /cost reads the token_count variable.  <!-- 20260501-171015.jsonl#0 -->
- The fluid-control demo lives in fluid-control/: index.html is the UI shell and its only script tag is fluid.js (app.js was written but not referenced); fluid.js is the engine and exposes its API via the window.Fluid object with step, project, setBnd, N, IX, SIZE, plus computeControlForce.  <!-- 20260911-143354.jsonl#1 -->
- The canvas pixel size is set in app.js (overriding the width/height attributes in index.html); its on-page display size comes from the CSS block in index.html, so both files must be changed to make the view bigger.  <!-- 20260911-143354.jsonl#4 -->
- The smoke control forces and solver live in fluid-control/fluid.js: computeControlForce() builds the target/cleanup forces, project() runs the Jacobi pressure projection, and the velocity-magnitude clamp constant V_MAX is applied just after setBnd inside the solver.  <!-- 20260911-143354.jsonl#5 -->
- The cleanup toggle's default state and its documented cost are in fluid-control/index.html (checkbox id "cleanup"); the tuning constants CLEANUP_SCALE and V_MAX and the force-field outer-loop check that zeroes force outside the target region live in fluid-control/fluid.js.  <!-- 20260911-143354.jsonl#7 -->
- fluid-control/fluid.js implements the paper's control forces: the Eq. 4 long-range force accumulates over target cells (guard on pt[IX(i,j)] > 0 inside the per-j summation) and writes fu/fv scaled by FORCE_SCALE; the Eq. 5 cleanup is the separate term. The target-cell guard must NOT be applied at the outer field loop.  <!-- 20260911-143354.jsonl#8 -->

## Habits
- When investigating how a feature is implemented in this repo, don't rely on docs_toc/docs_search (the knowledge base is game-engine docs like docs/godot/*.md and returned no matches for 'slash command' or 'help'); switch to grep/read over the actual source files to find the command-dispatch and help-listing code.  <!-- 20260501-135531.jsonl#0 -->
- When a tool rejects a call for a missing argument (e.g. assumptions), retry the same tool with the actual required content (one '- <item>' per line) rather than re-invoking a different planning tool.  <!-- 20260501-140243.jsonl#0 -->
- plan_write requires the whole plan body inline between the opening and closing <tool> tags; sending only the slug gets rejected and costs a round trip.  <!-- 20260501-142925.jsonl#0 -->
- When a tool is rejected because the current plan phase forbids it, do not retry it or sibling variants — switch to tools the phase allows or advance the phase (/plan accept).  <!-- 20260501-155330.jsonl#0 -->
- Never read a guessed file path: confirm the file exists (listing/search/context tool) before opening it, or you burn a call on a guaranteed error.  <!-- 20260501-155330.jsonl#0 -->
- If plan_write is rejected for a missing required section, resubmit the same slug with the section added; do not abandon the existing plan file and start over, which collides with the already-created file.  <!-- 20260501-171015.jsonl#0 -->
- Once a grep with a broad pattern returns the wrong/unrelated match, switch to a precise anchored pattern (e.g. include the surrounding `strcmp(user_input, "...")` code) and read the region once, rather than re-issuing several near-identical greps to locate the same symbol.  <!-- 20260501-172226.jsonl#0 -->
- Terminate every apatch hunk with '@@ END'; omitting it aborts the edit.  <!-- 20260501-184128.jsonl#0 -->
- When successive greps in the same file return nothing, stop re-grepping that file — enumerate repo files or grep across the tree to find where the code actually lives before concluding the expected structure exists.  <!-- 20260501-204329.jsonl#0 -->
- When using the bash tool for pipelines or complex shell commands, pass the command directly as arguments (e.g. `bash grep -n 'pat' file`); do NOT wrap it in `bash -c "..."`, which fails. Also, the dedicated grep/head/tail tools reject `|` and other shell operators — use bash for pipelines instead.  <!-- 20260501-205119.jsonl#0 -->
- Never repeat the exact same tool call with the same arguments after a result; the harness blocks it, so change the query or ask the user instead.  <!-- 20260501-210556.jsonl#0 -->
- When a search/fetch tool returns empty or unusable results, stop retrying it with rephrased queries after one or two attempts and either answer from general knowledge or say the sources were unhelpful — don't burn a loop of near-identical calls.  <!-- 20260505-142140.jsonl#1 -->
- Don't claim an answer is 'based on my research' when the tool results contained no usable content; either cite what was actually retrieved or state plainly that you're answering from general knowledge.  <!-- 20260505-142140.jsonl#1 -->
- For questions asking for the "latest version" of a package/project, verify the exact version against its official release page or repository (e.g., GitHub releases/tags, project download page) before answering; do not state version numbers from search snippets or prior knowledge.  <!-- 20260617-002539.jsonl#6 -->
- When a user corrects a factual claim, re-verify against the fetched primary source and cite the exact version string found there; do not re-assert another number from memory and dress it up with invented release dates or feature lists.  <!-- 20260617-002539.jsonl#7 -->
- If a re-search does not actually surface authoritative confirmation of the specific fact asked (e.g. the version number on the official download/release page), say so and give the source URL instead of guessing — a confident wrong answer after being corrected wastes the user's time.  <!-- 20260617-002539.jsonl#7 -->
- Before running `cd <dir> && ...`, verify the directory exists (or skip `cd` and use absolute paths); don't assume a working directory is present, since a failed cd aborts the whole chained command.  <!-- 20260707-202505.jsonl#2 -->
- After fetching a document, don't re-read text you already have; the read tool warns when content duplicates an earlier result. Navigate long fetched documents with targeted grep/sed instead of full re-reads, which waste context.  <!-- 20260911-132719.jsonl#1 -->
- Before summarizing multiple fetched documents, confirm you actually read each one: track which temp file each fetch produced and read the body of every fetched source, rather than reading one file and asserting you read them all.  <!-- 20260911-143354.jsonl#0 -->

- Before claiming a code path (e.g. an equation/feature) is implemented, verify it actually executes: check the call site and any flag/gate that enables it, and run it if possible.  <!-- 20260911-143354.jsonl#3 -->
- When fixing or rescaling one parameter/force, hunt for the parallel sibling paths that need the same treatment; fix and report all of them.  <!-- 20260911-143354.jsonl#3 -->

- When writing a comment that justifies a constant by a derivation, verify the arithmetic actually yields that constant in the stated units before shipping it.  <!-- 20260911-143354.jsonl#6 -->
- Before proposing an architecture-level fix (e.g. domain-wide reach for a force), read the existing field code for gating conditions that zero the quantity outside a region — otherwise the fix won't help because the field is clipped by an early-out, not by range.  <!-- 20260911-143354.jsonl#7 -->
